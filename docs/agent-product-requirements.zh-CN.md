# 数据处理 Agent 产品需求梳理

## 1. 产品定位

本产品是一个自然语言驱动、能够自主扩展能力的数据处理 Agent。

用户只需要描述已有数据、处理目标、期望输出以及质量、成本、时效或资源要求。Agent 负责将自然语言需求转化为完整的数据处理 Pipeline，并完成需求澄清、能力选择、方案比较、能力补齐、运行验证、结果交付和能力沉淀。

核心价值是：

> 用户描述目标，Agent 寻找并验证实现路径；已有能力直接组合，缺失能力自主补齐，经过验证的能力沉淀为可复用算子。

它不是一个只会生成 Data-Juicer 配置的助手，也不是一个根据关键词推荐算子的搜索工具，而是数据处理任务的分析者、方案设计者、能力建设者、受控编排者和结果交付者。

## 2. 目标用户与适用场景

### 2.1 目标用户

- 不希望直接编写复杂 Recipe、脚本和环境配置的业务人员；
- 需要快速建设数据处理流程的数据工程人员；
- 需要管理、复用和共享算法能力的团队；
- 需要对处理过程、执行结果和能力来源进行审查的管理员。

### 2.2 典型场景

- 文本清洗、过滤、去重、抽样和质量评估；
- 图片筛选、分类、打标、Mask 生成和质量分析；
- 视频分类、运镜判断和片段筛选；
- 多模态数据处理和数据集构建；
- 多阶段处理 Pipeline 的设计和执行；
- 多个候选 Pipeline 的效果、效率和成本比较；
- Data-Juicer 内置能力不足时的新能力建设；
- 用户自定义算子的管理、复用、共享和贡献。

## 3. 核心产品目标

系统应完成以下六个闭环：

```text
自然语言需求
  → 明确并确认需求
  → 设计和比较 Pipeline
  → 选择或补齐处理能力
  → 验证、审批和执行
  → 交付结果并沉淀能力
```

具体目标包括：

1. 用户无需理解全部 Data-Juicer 算子和运行环境，也能表达数据处理目标。
2. Agent 能把业务目标转化为可执行、可验证的 Pipeline。
3. Agent 能判断现有算子是否真正满足业务语义，而不是只做名称匹配。
4. Agent 能在能力不足时自主寻找算法或模型、开发算子、构建环境并完成验证。
5. Agent 能比较多个实现方案，并根据用户偏好推荐更合适的方案。
6. 每个正式 Pipeline 都可审查、可版本化、可批准、可复现和可追溯。
7. 每次运行的结果都能按照预先确定的验收标准进行验证。
8. 用户创建的算子能够被独立管理和复用，优秀算子能够经过审批进入公共算子库。

## 4. 核心领域概念

### 4.1 需求定义

需求定义是用户确认后的数据处理目标，至少包含：

- 输入数据及其模态；
- 处理对象和处理粒度；
- 目标效果；
- 输出数据和附属报告；
- 语义边界；
- 硬性约束和偏好；
- 可判定的验收标准；
- 时间、算力、成本和隐私要求。

### 4.2 原子需求

原子需求是可以独立验证的最小业务行为。原子需求描述业务语义，不等同于一个算子名称。

一个原子需求可能需要多个算子共同实现，一个算子也可能覆盖多个相关原子需求。

### 4.3 算子

算子是具有明确输入、输出、参数和处理语义的可复用执行单元。算子可以是：

- Data-Juicer 内置算子；
- 已批准的公共算子；
- 团队共享算子；
- 用户私有算子；
- 当前任务中的实验性算子。

### 4.4 Pipeline

Pipeline 是围绕一个任务目标组织的有序处理方案，包含：

- 处理阶段；
- 算子及其确定版本；
- 算子顺序和参数；
- 阶段间数据契约；
- 模型和依赖；
- 资源要求；
- 输入和输出契约；
- 验收标准及其步骤映射；
- 风险与已知限制。

Pipeline 不是简单的算子列表，而是完整、可执行、可验证的数据处理方案。

### 4.5 能力

能力是对一个或多个原子需求的已验证实现，可以由一个或多个算子、模型、依赖和运行策略组成。

能力不等同于 Docker 镜像，也不等同于某个模型名称。它必须具有稳定的数据契约、版本、测试证据和安全边界。

## 5. Agent 核心能力要求

### 5.1 需求理解与澄清

Agent 应能够：

1. 从自然语言中提取目标、输入、输出、约束和验收标准；
2. 主动检查可以从输入数据中获取的客观事实；
3. 区分已知事实、可自行发现的信息和必须由用户决定的问题；
4. 只询问会实质改变 Pipeline 的关键问题；
5. 不重复询问用户已经明确说明的要求；
6. 不把推测写成已经确认的事实；
7. 将需求整理成结构化摘要并交由用户确认。

需求澄清应尽量快速收敛，不应退化成逐字段问卷。

### 5.2 Pipeline 自动设计

Agent 应根据需求自动拆分处理阶段，例如：

```text
输入检查
  → 数据清洗
  → 内容识别
  → 质量过滤
  → 转换或生成
  → 去重与采样
  → 输出整理
  → 质量验收
```

Agent 负责确定：

- 每个阶段需要完成的业务行为；
- 应使用哪些算子；
- 算子的执行顺序；
- 算子参数；
- 是否需要模型或外部工具；
- CPU、GPU、内存和存储需求；
- 中间结果和最终结果的组织方式；
- 每条验收标准由哪些步骤负责；
- 如何验证整个 Pipeline 达到目标。

### 5.3 现有算子检索与语义判断

Agent 应优先从 Data-Juicer 算子库及已批准能力库中寻找可复用能力。

检索和选择不能只依赖名称相似度。Agent 必须检查：

- 算子的真实输入和输出；
- 算子的处理语义；
- 参数含义和默认行为；
- 支持的数据类型；
- 适用范围和已知边界；
- 性能和资源成本；
- 是否完整覆盖用户的硬性验收标准。

如果算子只能近似满足需求，Agent 必须明确说明差异，不得把近似能力描述为完整覆盖。

### 5.4 缺失能力识别

当现有算子不能覆盖全部硬性要求时，Agent 应明确报告能力缺口，包括：

- 哪一条原子需求无法满足；
- 当前最接近的算子是什么；
- 它为什么仍然不满足；
- 缺口会影响哪条验收标准；
- 是否存在可接受的降级方案；
- 是否值得建设新的可复用能力。

Agent 不得为了让 Pipeline 看起来完整而加入对最终结果没有作用的装饰性算子。

### 5.5 自主能力补齐

当现有能力不足时，Agent 应能够根据任务特点选择补齐方式：

- 编写轻量规则算子；
- 查找和复用成熟开源实现；
- 查找并选择合适的模型；
- 封装已有算法、模型或工具；
- 开发新的 Data-Juicer 兼容算子；
- 准备并锁定依赖；
- 获取并校验模型权重；
- 构建隔离运行环境；
- 编写自动化测试和效果评测；
- 部署新能力并加入当前 Pipeline。

补齐方式应遵循以下原则：

1. 简单规则优先使用轻量实现；
2. 成熟开源实现优先评估复用；
3. 只有确有必要时才引入更大、更贵的模型；
4. 面向同类数据可复用的算法应封装为正式算子；
5. 一次性实验可以使用受控原型，但不能冒充正式可复用能力；
6. 正式能力不得依赖不可复现的临时安装和环境修改。

### 5.6 方案比较与推荐

当存在明显的实现选择时，Agent 应形成多个候选 Pipeline，例如：

- 纯规则方案；
- 传统算法方案；
- 小模型方案；
- 大模型或多模态模型方案；
- 速度优先方案；
- 质量优先方案；
- 成本优先方案；
- 最大化复用已有算子的方案。

Agent 应从以下维度比较候选方案：

| 维度 | 比较内容 |
|---|---|
| 目标符合度 | 是否覆盖全部需求和验收标准 |
| 效果质量 | 准确率、召回率、稳定性和边界表现 |
| 运行效率 | 处理速度、吞吐量和延迟 |
| 资源消耗 | CPU、GPU、内存和存储 |
| 使用成本 | 模型调用、基础设施和维护成本 |
| 泛化能力 | 是否只适合当前样本 |
| 可解释性 | 是否能说明处理和淘汰原因 |
| 可复用性 | 是否可用于其他同类任务 |
| 安全风险 | 许可证、供应链、隐私和网络风险 |
| 维护成本 | 依赖复杂度、模型体积和升级难度 |

Agent 的推荐必须说明：

- 推荐哪个方案；
- 推荐依据；
- 相比其他方案的优势；
- 需要付出的代价；
- 哪些结论已经验证；
- 哪些结论仍属于预期或推断。

如果用户没有指定偏好，Agent 可以推荐综合最优方案；如果用户明确强调质量、速度、成本或可解释性，则应按用户目标调整比较权重。

### 5.7 验证驱动的方案选择

理论可行不能直接等同于方案更好。Agent 应能够：

1. 为候选方案设计小规模验证；
2. 选择具有代表性的样本；
3. 按验收标准运行和评分；
4. 比较不同方案的质量、速度和资源消耗；
5. 分析误判和边界案例；
6. 调整算法、算子顺序或参数；
7. 推荐有证据支持的最终方案；
8. 获得批准后再执行正式数据。

如果多个方案效果接近，应优先选择更简单、更便宜、更稳定且更容易维护的方案。

重要任务应区分调试样本与独立验证样本，避免在同一数据上调参和验收后错误宣称方案具有泛化能力。

## 6. 完整业务流程

### 6.1 标准流程

```text
用户描述数据处理需求
  ↓
Agent 检查输入事实
  ↓
形成并确认需求定义
  ↓
拆解原子需求
  ↓
检索内置算子和已批准能力
  ↓
判断现有能力是否完整覆盖
  ├─ 是：形成候选 Pipeline
  └─ 否：报告能力缺口
           ↓
         研究、开发或引入新能力
           ↓
         构建、测试和效果验证
           ↓
         能力审批与发布
  ↓
比较候选 Pipeline
  ↓
向用户推荐方案并说明依据
  ↓
用户确认方案
  ↓
生成不可变的正式 Plan
  ↓
展示执行预览、资源、风险和版本标识
  ↓
用户批准执行
  ↓
隔离运行
  ↓
按照验收标准验证结果
  ↓
发布到聊天和结果中心
  ↓
沉淀 Pipeline、算子和运行经验
```

### 6.2 用户确认与审批门禁

正式流程至少包含三道用户门禁：

1. **需求确认**：确认系统对目标和验收标准的理解；
2. **方案确认**：确认准备采用的 Pipeline 和主要取舍；
3. **执行审批**：确认具体 Plan 版本可以正式运行。

首次引入或实质修改源码、模型、依赖、许可证或权限时，还需要一次独立的能力审批。

已批准能力被后续任务复用时，不应重复要求能力审批。

## 7. 用户自定义算子管理

### 7.1 管理要求

每个自定义算子至少应记录：

- 稳定标识和显示名称；
- 所属用户或团队；
- 功能说明和适用范围；
- 输入、输出和参数定义；
- 源码及版本；
- 模型及固定版本；
- 依赖和运行环境；
- 来源和许可证；
- CPU、GPU、内存和存储需求；
- 自动化测试结果；
- 效果评测结果；
- 已知限制和风险；
- 创建时间和更新时间；
- 被哪些 Pipeline 和 Run 引用；
- 当前生命周期状态。

### 7.2 生命周期

建议的算子生命周期为：

```text
草稿
  → 构建中
  → 验证中
  → 用户私有可用
  → 团队共享
  → 申请贡献
  → 审核中
  → 公共算子库
  → 已弃用
```

### 7.3 用户操作

用户应能够：

- 查看自己的全部算子；
- 按类型、状态和标签搜索；
- 查看版本、测试和评测记录；
- 创建新版本；
- 将算子加入 Pipeline；
- 查看算子被哪些任务引用；
- 删除未被引用的草稿；
- 停用存在问题的版本；
- 申请团队共享；
- 申请贡献到公共算子库。

已经运行的 Pipeline 必须继续引用当时的确定版本，不能因为算子后来更新而发生隐式变化。

## 8. 算子贡献与公共算子库

### 8.1 贡献条件

适合进入公共算子库的算子应满足：

- 解决通用问题，而非只包含某个用户的临时业务逻辑；
- 输入输出契约清晰；
- 参数设计合理；
- 具有充分的单元测试和集成测试；
- 具有代表性数据上的效果证据；
- 依赖和模型来源明确；
- 许可证允许使用和分发；
- 不包含用户数据、密钥和私有路径；
- 资源消耗处于可接受范围；
- 已知限制得到明确记录；
- 与现有算子不存在不必要的重复。

### 8.2 贡献审批材料

贡献申请至少应包含：

- 算子功能和适用范围；
- 源码和依赖清单；
- 模型、来源和内容校验信息；
- 自动化测试结果；
- 效果评测；
- 性能和资源数据；
- 安全检查；
- 许可证证据；
- 与现有算子的差异；
- 已有真实使用案例。

### 8.3 审批结果

审批人可以：

- 批准进入公共算子库；
- 要求修改后重新提交；
- 拒绝贡献；
- 建议与已有算子合并；
- 仅批准为团队共享能力；
- 标记为实验性公共算子。

公共版本应成为独立、稳定的算子版本。用户原始私有版本继续保留，不应被公共版本直接覆盖。

## 9. Pipeline 管理与复用

每个正式 Pipeline 应保存：

- 用户原始目标；
- 确认后的需求定义；
- 原子需求及能力映射；
- 算子及确定版本；
- 算子顺序和参数；
- 模型、依赖和运行环境；
- 输入和输出契约；
- 验收标准；
- 验证结果；
- 性能和成本数据；
- 创建者和可见范围；
- 历史版本；
- 实际运行记录。

优秀 Pipeline 可以保存为模板。Agent 收到新需求时，应依次判断：

1. 是否存在可直接复用的 Pipeline；
2. 是否可以调整已有 Pipeline；
3. 是否需要重新组合现有算子；
4. 是否存在真正的能力缺口。

## 10. 运行、结果与追溯

### 10.1 受控执行

Agent 可以进行判断、研究和编排，但正式执行应由受控运行模块完成。

正式运行应具备：

- 明确的 Plan 版本和内容标识；
- 固定的算子、模型和依赖版本；
- 输入快照；
- 隔离的运行环境；
- 明确的 CPU、GPU、内存、存储和时限；
- 默认受限的网络权限；
- 输出范围和容量限制；
- 取消、失败恢复和清理机制。

Agent 不应直接控制底层容器权限，也不能通过临时修改共享环境绕过正式能力和运行流程。

### 10.2 结果交付

任务完成后，应向用户交付：

- 实际执行的 Pipeline 和 Plan；
- Run 和运行环境标识；
- 输入快照标识；
- 输出文件及完整性信息；
- 数据集结果；
- 标签、质量指标和媒体变体；
- 处理报告；
- 每条验收标准的结果；
- 已知限制和失败信息。

结果应进入用户自己的结果中心，支持浏览、筛选、预览、下载和追溯。

### 10.3 可追溯性

以下对象应具有稳定标识、版本和必要的内容校验信息：

- 需求定义；
- Pipeline 和 Plan；
- 算子；
- 能力；
- 模型；
- 依赖；
- 运行环境；
- 输入快照；
- Run；
- 最终业务输出。

## 11. 权限与共享模型

能力至少分为四个可见层级：

| 层级 | 可见范围 |
|---|---|
| 任务临时能力 | 仅当前任务 |
| 用户私有算子 | 仅创建用户 |
| 团队共享算子 | 指定团队或部门 |
| 公共算子库 | 所有具备权限的用户 |

Pipeline、模型、源码、依赖、输入数据和处理结果也应遵循明确的归属与授权规则。

Agent 不能因为知道某个私有能力存在，就向其他用户泄露其名称、功能、源码、模型或数据。

## 12. 能力知识库与持续优化

公共算子库不应只是静态文件列表，还应积累真实任务中的使用反馈，包括：

- 使用次数；
- 成功率和失败率；
- 常见数据规模；
- 平均运行时间；
- CPU、GPU、内存和存储消耗；
- 典型效果指标；
- 常见错误；
- 适用和不适用场景；
- 用户评价；
- 常见组合方式；
- 被替代或弃用的原因。

Agent 可以利用这些信息判断：

- 哪个算子更稳定；
- 哪个模型效果更好；
- 哪个实现成本更低；
- 哪些算子经常一起使用；
- 哪些能力已经不再推荐；
- 是否存在可直接复用的公共 Pipeline 模板。

系统应逐步从静态算子库演进为基于真实任务经验的能力知识库。

## 13. 系统职责边界

| 组件 | 主要职责 |
|---|---|
| Agent | 需求理解、澄清、能力判断、方案设计、代码生成、比较推荐和用户交互 |
| 能力目录 | 提供内置、私有、团队和公共能力事实 |
| 能力治理模块 | 管理源码、模型、依赖、测试、许可证、审批和发布 |
| Pipeline 管理模块 | 保存 Pipeline、版本、参数、验收映射和复用模板 |
| 运行环境解析模块 | 将 Pipeline 所需能力组合成确定的运行环境 |
| 执行模块 | 按固定安全策略运行任务并管理生命周期 |
| 结果中心 | 登记、授权、展示、筛选和下载处理结果 |
| 身份与权限模块 | 管理用户身份、资源归属和访问控制 |

系统坚持单 Agent 负责业务理解和决策。其他模块提供确定性的事实、治理、持久化和执行能力，不应演变为多个 Agent 相互对话的不可控系统。

## 14. 产品体验要求

对用户而言，完整体验应尽量接近：

1. 用户自然语言描述目标；
2. Agent 检查输入并澄清少量关键问题；
3. Agent 给出一个或多个 Pipeline 方案；
4. Agent 说明推荐方案、证据和取舍；
5. 如果缺少能力，Agent 自动寻找实现或开发算子；
6. 新能力完成构建、测试和效果验证；
7. 用户确认最终 Pipeline；
8. Agent 提交受控运行并持续报告状态；
9. Agent 按验收标准检查结果；
10. 用户在聊天和结果中心浏览、筛选和下载结果；
11. 新算子进入用户能力空间；
12. 表现优秀的算子可以申请贡献到公共算子库。

技术复杂度应尽量由 Agent 和平台承担。用户需要看到的是目标、方案、差异、风险、成本、证据和结果，而不是大量安装命令和环境配置。

## 15. 产品约束与反目标

本产品不应退化为：

- 根据关键词随意推荐算子的搜索机器人；
- 不确认需求就直接执行的自动化脚本；
- 遇到缺口就修改共享环境的万能 Shell Agent；
- 用不等价算子近似满足要求却不声明差异的方案生成器；
- 把结构校验成功当成业务结果正确的执行器；
- 每次任务都重新下载模型和重新构建能力的低效流水线；
- 只返回日志和文件路径、没有用户可消费结果的后台系统；
- 无法说明推荐依据和方案取舍的黑盒；
- 因算子升级而隐式改变历史 Pipeline 行为的非版本化系统。

## 16. 总体验收要求

理想产品至少应满足以下验收要求：

1. 用户可以仅用自然语言发起完整的数据处理任务。
2. Agent 能形成可确认、可判定的需求和验收标准。
3. Agent 能正确识别已有能力、部分覆盖和真实能力缺口。
4. Agent 能生成语义正确且结构有效的 Pipeline。
5. Agent 能在多个合理方案之间进行有证据的比较和推荐。
6. 缺失能力能够通过受控流程完成开发、引入、测试、审批和部署。
7. 新能力可以被后续任务直接复用，不重复构建和审批。
8. 正式运行具有确定版本、隔离环境、资源限制和完整追溯信息。
9. 运行结果能够逐项对应任务的验收标准。
10. 用户可以管理自己的算子、Pipeline 和结果。
11. 私有、团队和公共能力之间具有清晰的权限边界。
12. 优秀自定义算子可以经过完整证据审查后进入公共算子库。
13. Agent 能利用历史运行和评测数据持续改进方案选择。
14. 历史 Pipeline 和 Run 不受后续算子、模型或环境升级的隐式影响。

## 17. 最终产品定义

> 一个面向数据处理和数据集构建的智能 Agent。用户通过自然语言描述目标，Agent 自动完成需求澄清、Pipeline 设计、算子选择、方案比较和结果验收。Agent 优先复用 Data-Juicer 及能力库中的已有算子；当现有能力不足时，可以自主开发算子，或寻找、部署合适的算法与模型，并将其作为受管理、可复用的能力加入 Pipeline。用户产生的自定义算子在个人或团队空间中进行版本化管理，经过实际任务验证的优秀算子可以申请贡献，经审核后进入公共算子库。系统通过持续积累运行效果、成本和适用边界，使 Agent 能够不断给出更准确、更高效、更符合用户目标的 Pipeline 方案。
