# DSH → Pi 完整迁移方案

日期：2026-09-12。状态：设计与实施计划，尚未执行迁移。

## 1. 目标与完成定义

基于 Pi 源码建立自己的数据处理 Agent 产品，最终运行不依赖 DSH。保留 Data-Juicer 处理底座及已实现的业务资产。用户在同一会话中提出任务，必要时回答澄清问题，审查准确方案，得到后台执行进度和主动结果报告；已有能力不够时，Agent 开发并验证自定义算子后继续原任务。

完整迁移包含：对话与模型配置、按需澄清、工具调用、可信方案审批、任务恢复、后台运行和取消、主动报告、账号与工作区授权、算子库、方案查看、结果中心和下载，以及历史业务资产访问。

Pi 终端接通 DJ 仅是第一个里程碑。新系统必须能在 DSH 不启动、旧 DSH 插件不加载的情况下独立完成上述功能。

本次只写方案，不安装 Pi、不创建远程 Fork、不修改现有运行服务、不迁移数据库。此前调研与当前代码是设计依据，并非已经完成 Pi 联调或性能比较。

## 2. 明确的技术选择

| 项目 | 选择 | 原因 |
|---|---|---|
| Agent 内核 | Fork Pi 源码，固定一个通过验证的提交 | 可持续修改，避免跟随浮动 main |
| 与 Pi 的关系 | 产品与 Pi 位于同一源码仓库；通过其公开 SDK/扩展接口接入 | 拥有源码不等于所有业务都要写进内核 |
| 产品语言 | TypeScript/Node，Web 使用 React | 复用现有 JS/React 业务代码 |
| Web 宿主 | 独立 Node HTTP 宿主，REST 写入、SSE 推送事件 | 不再依赖 Cordis、DSH ApiProxy、slot 或内部会话协议 |
| 会话执行 | 宿主调度独立的 Pi 会话进程，通过自有窄 IPC 管理 | cwd、配置与生命周期隔离；进程隔离本身不是安全沙箱 |
| 业务控制 | 提取已有 PlanWorkflow、IdentityAccess、DatasetCatalog | 避免再造审批、身份和结果模型 |
| 数据执行 | 保留 DJ 服务及现有 worker | Plan/Run、依赖与算子验证继续复用 |
| 存储 | 初期保留 SQLite，Pi 会话文件单独保存 | 与目前单机部署一致，无需先引入 Redis/消息队列 |
| DJ 接入 | 第一阶段复用内部 HTTP；标准 MCP 独立适配并验收后启用 | 当前多账号、可信审批语义不能仅凭 MCP 连通就认定等价 |

Node 版本取“所选 Pi 提交支持范围”和现有 node:sqlite、crypto.argon2Sync 所需范围的交集，固定版本并运行启动测试；不直接套用任意 LTS。包管理器遵守 Fork 基线的仓库规范，不把现有 pnpm 配置硬搬入 Pi。

Pi 官方提供 SDK、扩展及包机制，可用于此方案。使用本地源码构建的 Pi 包，检查依赖解析路径，避免产品实际加载 npm 另一版本。保留上游许可证及版权声明。[SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)、[扩展](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)、[包机制](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md)、[许可证](https://github.com/earendil-works/pi/blob/main/LICENSE)

## 3. 目标结构与职责

```text
浏览器：聊天 / 待回答问题 / 方案 / 算子库 / 结果中心
                          │ REST + SSE
                          ▼
DJ 产品宿主（独立于 DSH）
  身份与授权 ── 会话目录与调度 ── 问答与审批 ── 结果投递
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
      Pi 会话进程                 后台任务监督
      本地 Pi SDK                审批派发、Run 同步
      DJ tools + skill           outbox 与交付记录
              │                       │
              └───────────┬───────────┘
                          ▼
                    DJ 工具客户端
                  HTTP / MCP adapter
                          ▼
         DJ 服务：目录、Plan、个人算子、Run、验收
                          ▼
                  现有数据处理 worker
```

建议新增目录如下，实施时按 Fork 基线工作区规范放置；这些是目标路径，不是现有文件：

```text
<pi-fork>/
  packages/                     # Pi 原有包保留
  apps/dj-web/                  # React 产品界面
  apps/dj-host/                 # HTTP、SSE、后台监督、Pi 会话调度
  modules/dj-control/           # 身份、问题、审批、任务绑定、outbox
  modules/dj-client/            # 同一工具契约的 HTTP/MCP adapters
  modules/dj-pi/                # SDK 接线、工具注册、上下文与生命周期
  extensions/dj/                # Pi TUI 入口；调用同一业务模块
  skills/data-juicer/            # 主 skill 与按需 references
  tests/migration/              # 历史资产、恢复、双账号等测试
  deployment/                   # 配置模板、部署清单、启动与迁移命令
  docs/                         # 设计、升级和运维记录
```

不把所有 DJ 算子逐一变成 Pi 工具。Pi 获取少量业务工具，通过检索及 schema 选择具体算子。开发与正常规划用同一个面向用户的 Agent；缺口开发可使用受限上下文，不在第一版引入多 Agent 团队。

## 5. 工具与身份接线

### 5.1 一个目录，两类工具

DJ 工具继续复用 inspect_input、search_capabilities、get_capability_schemas、get_plan_contract、prepare_plan、get_plan、get_run、cancel_run、inspect_runtime 及自定义算子相关工具。

宿主补充 ask_user_question、confirm_plan、get_workflow_status。保持 skill 中的业务名称；若选择保留 mcp__dj__ 前缀，所有引用必须统一。不要同时注册同义工具让模型重复选择。

模型不直接获得 approve_plan。正式 run_plan 也由审批派发器调用；模型收到的 confirm_plan 结果包含既有 Run 或 queued 回执，不再主动调用 run_plan。

### 5.2 统一调用上下文

内部调用上下文建议包含 actor_id、product_session_id、workspace_ref、tool_call_id、request_id、deadline 和取消信号。它由可信宿主产生，不作为模型可编辑参数。保留当前工作区登记与 task owner 检查。

工具参数继续用 DJ 公开 schema 做校验；宿主注入身份、真实工作区和请求身份。将 Pi 实际调用 ID 与业务 request_id 持久映射，恢复时不能临时生成新键。执行幂等以审批 attempt 为准，不能仅靠每次变化的模型调用 ID。

### 5.3 HTTP 与 MCP 的具体取舍

第一版以现有内部 HTTP 为正式通路，维持服务握手、版本校验、账号归属、可信审批及作业语义。这仍是“Pi 完全替换 DSH”，并不依赖 DSH 进程。

MCP adapter 使用标准客户端完成工具发现、schema 转换、callTool、超时和错误处理。接入前验证其与 HTTP 的账号、工作区、审批身份和取消语义等价；当前源码中的 MCP instructions 还写着 DSH session，应改为宿主中立描述。

若当前标准 MCP 无法传递并验证可信账号，不得默认匿名访问生产任务。可通过产品网关提供经认证的 MCP 入口或先保持正式写操作走 HTTP。必须向使用方明确真实 transport，不能把内部 HTTP 宣称为标准 MCP。

## 6. 追问、审批与恢复

### 6.1 追问

模型调用 ask_user_question → 宿主写入 question_id、问题版本、会话归属及 pending 状态 → TUI 或 Web 展示 → 用户回答由宿主验证并持久化 → 返回工具结果。

简单 TUI 使用 Pi ui.select/input；Web 使用自建问题卡调用同一回答路由。无交互终端时返回等待状态，不使用默认答案继续。问答超时、取消和不支持 UI 都不等于批准。

问题挂起时进程可能消失，所以 pending 不能只存在 Promise 中。恢复时用持久答案完成对应工具结果；若固定 Pi 版本不支持原位恢复未闭合工具调用，则由 adapter 生成明确的中断结果，再注入已保存答案继续，不能重放有副作用的工具。此项必须用故障注入验收。

### 6.2 方案审批

confirm_plan 输入仅为 task_id、plan_version、content_hash 和可选 retry_of。宿主重新读取 Plan，检查内容、阻断项和未决需求，展示准确方案、缺口、输出及成本。真实用户选择形成 decision，再由派发器幂等批准并运行。

已有 decision/request 重放返回同一结果。修改执行内容必须新版本；失败 Run 重试生成独立 attempt，保留旧结果。Pi fork 会话不会复制审批权限或自动启动任务，是否续接旧 task 由宿主明确绑定。

### 6.3 规划恢复

持久保存当前目标、已知输入、shortlist、schema 版本、coverage、candidate_id、Plan/Run 引用和 pending_action。Pi 管聊天历史，业务模块管准确业务事实；不维护第二份可变 recipe 副本。

通过 get_workflow_status 恢复，不要求模型解析旧 DSH 日志。需求明确时不额外确认；可从输入检查得到的事实不交给用户填表。保留正常探索弹性，不强制所有任务按固定次数检索。

## 7. 后台运行与主动报告

后台监督器位于宿主，不在 Pi 扩展的临时计时器里。审批后返回运行回执；Pi 会话可以停止、压缩或退出，DJ Run 继续运行。

运行监督器有租约和退避，查询 DJ 事实。发现终态，在数据库事务中更新投影并写入 outbox；唯一键使用账号、run_id、report_version、目标产品会话。消费端幂等保存持久结果消息，随后推送 SSE。失联客户端按事件游标补读；进程在投递前后崩溃也不能丢结果或重复卡片。

结果默认用结构化摘要直接显示：输入/输出数、产物、执行状态、交付状态、验收条目与失败原因。需要自然语言解释时再唤起对应 Pi 会话。模型失败不阻止基本交付；不伪造用户消息来触发总结。

TUI 仅向当前绑定会话投递；切换到其他会话时保留未读结果，恢复原会话后补送。用户取消后仍收到取消结果，但不自动续跑。清理结束与模型停止是不同动作，分别验证。

SSE 实时 token 可短期缓存；审批、问题、终态和结果是持久业务事件。重连拿快照及游标，不要求永久保存每个 token delta。

## 8. DJ 后端必须一起修复的体验问题

这些问题与选 Pi 无关，但不修就会随迁移带过去：

1. 增加规则组合：all/any/not、范围和集合匹配，明确 null/缺失值；用结构化表达与类型检查，禁止任意 eval。人脸数 0 或 ≥2 不再需要重做检测。
2. 区分打分、判定、交付。需要完整淘汰原因时统一消费全量评分；需要早停时记录 not_evaluated，不能谎称全部评估。
3. 公开标签/API VLM 输出及执行分支契约，支持猫狗等分组输出。API 分支不能因本地无 GPU 被排除；不把照片风格等同来源真实性证明。
4. 自定义验证支持明确的嵌套路径格式，返回字段存在性、expected/actual 和有界样例。采用一种明确路径规范并保留旧字段兼容，不混用含糊点号。
5. 完成静态/契约预检后才扣真正执行预算；请求重放不重复扣费。返回剩余额度和实际可执行的恢复途径。
6. 修复候选以版本关联，保留失败证据，不鼓励修改名称或删除断言绕过限制。
7. 小样本完整链路验证覆盖结果字段、统计对齐、报告和输出文件。若涉及实际外发数据或收费，纳入明确的试跑授权；未经授权不因称为 canary 就执行。

这些项目应形成独立可回归改动，先在隔离 DJ 实例验证。迁移期间保持协议兼容，避免新旧入口共用一个不兼容 schema。

## 9. 自定义开发与模型控制

能力缺口形成有界工作项：业务目标、输入输出、已有证据、允许依赖、样本、验收与预算。开发上下文只处理该缺口；不要重新打开整条 Pipeline 的所有决策。

Pi 文件编辑与执行工具仅在受控候选目录工作。依赖安装、模型准备、发布和正式运行继续进入 DJ 作业系统；API 密钥与管理 token 不进入候选进程。共享环境维护是独立授权动作。

保留当前应用授权控制，但不将它冒充 OS 隔离。面向不可信多账号代码执行时，应使用已有可验证的容器 worker 或独立 OS 身份、目录权限和网络策略；多 Pi 子进程本身不能阻止跨账号读文件。

固定模型网关适配，测试工具参数流式分片、错误结果、取消、压缩后恢复和图像输入声明。规划与开发分别设置经验证的预算；发生无进展时保存证据、返回具体下一动作。不能靠 prompt 中写“120 秒内完成”保证收敛。

## 10. Web 产品迁移范围

第一版正式 Web 保留：登录、工作区与会话选择、聊天与工具进度、待回答问题、准确 Plan 确认、Run 状态/取消/重试、方案详情、算子目录/个人版本、结果列表/预览/下载、模型配置与连接状态。

主界面采用聊天区加方案/结果详情区，先保证功能等价。旧 React 业务视图可以提取，DSH 的 DOM 插入、conversationEvents、layout slot 和 ApiProxy 必须替换。

服务端必须检查会话列表、消息、SSE 订阅、问题回答、审批、结果预览/下载/删除的账号归属。保持现有 workspace registry 与账号 ID。浏览器登录令牌重新签发；不把旧 DSH 登录 cookie 直接当新宿主凭据。

模型设置存于服务端受控配置；浏览器只收到模型可用性，不能看到密钥。预览媒体和报告通过带授权的路由，不开放任意文件路径读取。聊天输出渲染按不可信内容处理。

## 11. 历史数据与切换

| 数据 | 策略 |
|---|---|
| DJ task / Plan / Run / 输入快照 | 原位保留 ID、hash 与 owner；不为迁移重新批准或重跑 |
| 个人算子、模型与依赖缓存 | 保留，按现有指纹验证；不强行重建所有模型缓存 |
| 用户与 workspace registry | 迁移备份副本并核对 ID；不重新猜测 owner |
| 审批、attempt、结果目录 | 版本化迁移脚本，保持幂等键和原始出处 |
| DSH 聊天历史 | 导出可读消息与业务引用作只读归档；不是转换成 Pi 原生执行历史 |
| 正在等待的旧问题/审批 | 不自动批准；在新入口重新展示准确版本并记录真实选择 |
| 正在运行的任务 | 最终切换前排空或明确取消；不由两个派发器并行接管 |

开发用独立产品数据库、测试账号/工作区和隔离 DJ 实例。试运行可以读取历史资产，但新旧宿主不得各持一份审批库同时向同一业务任务派发。

切换步骤：

1. 冻结受控版本，记录 Pi 提交、产品提交、DJ 构建、Node/Python 和 schema 版本。
2. 暂停旧入口新提交；排空活动 Run、开发 job 和待派发 attempt。
3. 使用 SQLite 备份接口或服务停止后的完整备份，不能在线只复制主 db 而漏 WAL。
4. 在副本 dry-run 迁移，核对用户、task、Plan hash、Run、结果数量及抽样产物 hash。
5. 停止旧派发器，启动新宿主及唯一监督器；重新登录并执行小数据验收。
6. 保留旧数据只读备份及回退安装包；新部署运行时不再启动 DSH。

回滚区分：尚无新写入，可恢复切换前部署；已有新写入，先停新提交、排空/记录新任务，核对兼容 schema 和新 ID 后再恢复旧入口。不得直接覆盖旧快照导致已批准任务、成果或审批丢失。新会话可暂时只读，新 DJ Run 必须仍可查询。破坏性 schema 升级在回滚窗口之后另做。

## 12. 分阶段实施与退出条件

| 阶段 | 交付 | 退出条件 | 粗估人日 |
|---|---|---|---:|
| P0 基线与 Fork | 固定源码、构建、独立配置、现状回归与资产清单 | 上游构建通过；当前故障可定位；部署可重现 | 1–2 |
| P1 提取业务模块 | Identity、Workflow、ResultCatalog、HTTP 客户端 | 不依赖 DSH 可运行原业务测试；审批重放不重复启动 | 2–4 |
| P2 Pi 纵向接通 | TUI、模型适配、DJ tools、skill、问题/审批 | 明确文本任务从输入到报告完整成功 | 2–3 |
| P3 完整恢复与后端修复 | 规则、验证、预算、持久问题、outbox、受控开发 | OR 无自定义；真实缺口可开发；崩溃/重放不丢结果 | 4–7 |
| P4 Web 等价迁移 | 登录、会话、审批、方案、算子、结果、下载 | DSH 停止后所有既有核心页面流程独立可用 | 4–7 |
| P5 演练与切换 | 数据迁移、回滚演练、发布清单、运行手册 | 双账号、恢复、历史访问及端到端验收通过 | 2–4 |

合计粗估 15–27 人日，为熟悉当前代码、模型/运行环境可用的工程估算，不是承诺日历工期。P2 只代表接通；完整迁移到 P5。未知的 Pi 基线兼容、OS 沙箱和历史数据问题可能增加工作量。

## 13. 验收矩阵

| 类别 | 必测行为 |
|---|---|
| 常规任务 | 明确文本清洗不额外确认需求；工具参数正确；成果可下载 |
| 澄清 | 模糊目标集中询问；已回答不重复；问答中重启后可继续 |
| 规则 | 人脸 0 或 ≥2；边界值、缺失值；不重新开发检测算子 |
| 视觉分类 | API/local 分支正确；猫狗同框策略明确；无标签进入复核 |
| 自定义 | 真正缺口开发、嵌套断言、错误反馈修复、预算拒绝、取消清理 |
| 审批 | 精确 hash、版本变更、用户取消、重复响应、越权回答 |
| 恢复 | 模型超时、工具响应丢失、Pi 被杀、宿主重启、浏览器关闭 |
| 幂等 | 提交前后断线只产生一个 Run；重试保留旧 Run |
| 交付 | 完成无需追问；模型不可用仍有报告；终态重复事件只显示一次 |
| 会话 | 切换/恢复后工具与事件重新绑定；fork 不复制审批；结果不串会话 |
| 多账号 | 文件、会话、事件、审批、结果和自定义代码执行的隔离 |
| 迁移 | 旧账号/资产 ID 与 hash 保留；历史只读可见；新写入后可控回退 |

继续保留现有 12 例规划评测的原始协议和 gold；它禁止部分扩展且不到执行阶段，不能直接充当完整产品验收。另增执行集，覆盖上述矩阵。

指标：首个有用动作、到可审批 Plan 的耗时、非用户等待耗时、模型 token、无效工具比例、Run 成功率、硬验收通过率、终态到可见结果的延迟。对可控低成本用例重复至少三次；模型比较使用相同输入和工具，不把更换模型带来的收益归功于 Pi。

建议发布目标：确定性关键回归全部通过；明确需求没有额外需求确认；简单 OR 不进入开发；重复提交不重复 Run；重启能恢复；本机正常状态下终态 5 秒内结果卡可见。质量未知明确标记，不将进程退出成功视为语义验收通过。模型任务阈值依据基线冻结，不编造“100% 成功”目标。

## 14. Fork 的长期维护

origin 指向自己的仓库，upstream 指向 Pi 上游；建立独立产品开发分支。新模块优先追加，不大面积改动原包。每个内核改动记录触发需求、无法用扩展完成的理由及回归案例。

更新上游在独立分支执行：检查许可证/依赖、构建、模型流式协议、工具调用、会话恢复、问答及完整业务回归，通过后才发布。部署清单固定依赖和源码身份，发布期间不自动拉取 main。

最终维护面为 Pi Fork + DJ 产品模块 + DJ 后端。DSH 保留为历史归档与回退材料，不进入新产品运行依赖。
