## 为什么没有使用 API VLM

当前可确认的内置候选是 image_tagging_vlm_mapper 的 API 模式，而不是名为 vlmapi 的独立内置算子。公开参数已有 is_api_model、api_or_hf_model、api_endpoint、system_prompt 等，设置 is_api_model=true 会走远程 API。原 trace 没有检查这组参数，不能说它尝试过但不可用。

只读复现命令：node .dsh/diagnostics/0a6482f0c46ee496d341843a4000b4ae/replay.mjs。重放三轮原查询，结果与 trace 一致，首轮 API VLM 召回检查为 FAIL；精确名称或 remote VLM API 查询能将它排在首位。这排除了算子根本未注册的解释，也证明检索不够稳健。

实际详情还有三项误导：

- gpu/api/vllm 是算子级混合标签，没有明确区分远程 API 和本地推理的资源需求。
- 未指定模式时详情展示本地 Qwen2.5-VL-7B 的 HF 权重锁；这不是 API 模式一定要下载本地权重的证据。
- output_contract=unknown，limitations 明确提示可做 bounded diagnosis；当前完整语义契约只重点覆盖此前五个数值 Filter。模型因此缺乏通过工具完成标签判定及分组输出的闭合路径。

执行实现输出的是逐图标签，位于 __dj__meta__ 的配置字段中；默认解析器消费 tags，不能假定任意 JSON 分类结构都会被完整保留。即使选中了 API 模式，也应定义稳定标签、失败/不确定结果、逐图对齐和猫狗分组输出契约。

本次没有调用真实 VLM、发送图片或检查私密凭证。因此结论是“API 路径存在且被忽略”，不是“当前 API 已经验证可用”。运行时实际配置、费用和质量应由后端检查及获准样本验证给出。

## 为什么又读源码

直接触发点是完成第一次参数查询后，模型转向寻找 mllm_mapper 实现，试图判断提示词和本地执行方式。没有结构化契约错误触发这次诊断。随后本地路径定位失败形成连续环境探索。

这里既有模型未继续检查已召回 API 候选的问题，也有工程接口问题：未知输出契约提供诊断建议，但未返回具体缺失项、必要事实及明确恢复动作；Skill 的调试例外和自定义开发入口没有对应的工程边界。正常规划与开发状态之间仍主要靠模型自觉判断。不能用“一律禁源码”修复，也不能把此次业务规划自动解释为获准修改共享运行环境。

## 修改建议

1. 能力发现按行为与执行模式建模：检测、分类、生成、变换应可区分；本地与 API 分支应分别说明资源、模型绑定和限制。保留语义检索并增加跨任务召回回归，不再只为五个已知阈值词补排名。top_k 截断需显式解释并提供扩展候选的途径。
2. 公开 API VLM 分支契约：输出字段、标签解析、逐图对齐、错误/空标签语义、远程数据发送及计费说明；后端只返回配置是否就绪和恢复动作，不暴露密钥。按已选分支返回资源需求，不把 API 调用描述成 GPU 的 CPU fallback。
3. 提供独立的结果判定和分组交付能力；不要强制套进只接受数值 Filter 的 image_audit。此任务可用视觉标签识别猫/狗及照片风格，再按规则分组，报告消费同一结果。猫狗同框和不确定样本要有显式处理策略。
4. 标准 preset 保留。由宿主/工具返回规划模型的输入能力，避免明知文本模型仍提供无效视觉读取路径。开发和诊断按具体目的进入受控路径：缺字段先查契约，运行失败先查结构化日志，确需实现细节再限定源码范围；自定义开发使用隔离作业，环境安装由锁定依赖流程负责。
5. 将“实拍风格判断”与“证明图片非 AI 生成”分开。VLM 可以作内容/风格分类，但其结果不能当拍摄来源证明。不得擅自增加美学筛选条件或承诺可靠排除所有逼真合成图。
6. 验收应覆盖本例等未见任务：首轮或有界补查能找到 API 候选；不因无 GPU 判定无能力；所有必要条件能通过公开契约表达；有明确执行确认；无无因源码遍历和共享环境安装；无解析结果时明确失败或进入复核，不能静默当作非猫狗。
