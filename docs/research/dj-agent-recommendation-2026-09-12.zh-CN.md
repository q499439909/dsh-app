# Data-Juicer 对话处理系统：现状与选型建议

日期：2026-09-12。范围：读取 D:/dsh-app、D:/dj/data-juicer-1.5.4 的当前实现、skill、评测与近期诊断记录，并调研官方框架资料。本次没有修改业务实现、升级依赖、重启服务或运行收费模型。历史 trace 指标引用已落盘审计，不冒充本次重新采集。选型是工程判断，尚无同模型端到端对照数据。

## 结论

推荐保留 DJ 后端，逐步提取独立的 DJ 应用运行层，以 **Pi SDK + 薄的专用 Web 应用**作为优先验证的目标方案。短期先在 DSH 修复共享后端断点；完成同条件验证后才切换入口。不要从零重写模型通信和工具循环，也不要把整个系统改写成 Deep Agents 后期待流程自然变顺。

这不是因为已证明 Pi 更聪明或更快，而是现有 Node 应用资产较多，Pi 提供可嵌入的 agent 能力，适合减少对 DSH 内部插件机制的依赖。用户可见体验仍应是一个对话、一份方案、一次执行和主动报告。

## 现有工作中值得保留的资产

- DJ 的算子检索、schema、Plan 版本与内容 hash、输入快照、异步 Run、取消、模型准备、个人算子验证和结果验收。
- DSH 的账号、工作区授权、可信审批、幂等派发，以及算子库、方案查看与数据集展示业务逻辑。
- 最新主 skill 已按需澄清，旧需求 skill 仅转入主入口；不是旧版本固定三次确认流程。
- 已有规划评测矩阵及图像夹具，可用于迁移对照。

证据：[当前 skill](D:/dsh-app/.dsh/skills/data-juicer-plan-flow-zh/SKILL.md)、[PlanWorkflow](D:/dsh-app/packages/dsh-user-auth/lib/plan-workflow.js)、[评测说明](D:/dsh-app/evals/dj-pipeline-planning-v1/README.md)。

当前 DSH 走内部 HTTP gateway；`mcp__dj__` 是兼容工具名称。标准 MCP 入口仍存在，但当前账号注入、confirm_plan、审批后的派发与结束本轮由宿主实现。因而不能把 MCP 地址换到另一 agent 就声称完整迁移。

证据：[接线](D:/dsh-app/dj-dsh.patch.yml)、[桥接实现](D:/dsh-app/packages/dsh-user-auth/lib/dj-bridge.js)。

## 第一性原理：把不确定判断与确定执行分开

模型适合理解目标、识别会影响结果的歧义、选择能力、提出参数和补写小段代码。程序适合数据类型校验、依赖检查、记录审批、运行恢复、重试去重、计算计数和可靠交付。

MCP 解决工具连接，不解决语义完备性和任务持久性；skill 能指导行为，不能替代代码约束。框架可以管理会话，却不能推导 DJ 的统计字段、业务规则和结果契约。

不建议把正常规划做成十多个状态逐个硬锁工具。保留灵活探索，但对正式执行条件、授权、开发工作项范围和无进展恢复建立明确实现。

## 候选方案

| 方案 | 收益 | 必须补的工作 | 判断 |
|---|---|---|---|
| 继续 DSH | 现有 UI、会话和业务集成最多 | 后端缺陷、主动报告、探索控制；持续维护内部补丁 | 最快短期修复路径 |
| Pi SDK + 薄应用 | Node 易复用、内核可嵌入、自定义工具与会话能力 | 问答/审批、账号、DJ adapter、终态投递、Web 展示 | 优先目标方案 |
| Deep Agents | Python 工具、文件/代码能力、持久化和人工中断的框架基础 | DJ 规则/验收/作业与 UI 仍需接入，且要协调两套持久状态 | Python 团队或大量复杂开发任务时更合适 |
| 完全手写 agent loop | 自由度最大 | 流式工具分片、恢复、压缩、取消、供应商协议等都要维护 | 当前不划算 |
| DJ 官方 agents / AgentScope | 同领域的工具与能力设计值得直接借鉴 | 现有账户、审批、个人资产、输出展示兼容性需验证 | 作为参考和对照，不立即替换 |

Pi 支持 SDK、JSONL RPC、自定义工具和会话管理；没有内置 MCP，直接接现有 HTTP 工具即可，外部 MCP 客户端按需添加。Deep Agents 支持更多现成编排基础，但 DJ 长任务并不会因换框架自动成为可靠完成并投递的任务。详见[框架资料](D:/dsh-app/docs/research/agent-framework-options-2026-09-12.md)。

DSH 当前本地依赖为 0.1.1-rc.2，维护 5 个 patchedDependencies。调研时官方 release 列表最新为 0.1.5-rc.2（预发布）；近期更新涉及 Session、Inbox、插件 Agent 与 Web 面板接口。升级可能改善模型适配与 UI，但需真实迁移，不是低成本修复所有业务问题的捷径。[官方发布记录](https://github.com/deepseek-ai/deepseek-harness/releases)

DJ 官方项目目前也强调可复用 tools、capabilities 和 skills，而不是继续按场景建设专用处理 agents；`dj-agents` 仍提供 AgentScope 对话入口。值得借鉴其与运行框架解耦的工具设计，不能依据旧多 agent 示例假定现成产品已覆盖本地治理需求。[官方路线](https://github.com/datajuicer/data-juicer-agents)、[官方架构](https://github.com/datajuicer/data-juicer-agents/blob/main/docs/overview.md)

## 推荐实现

```text
Web 对话 / 方案 / 结果
          ↓
DJ 应用运行层：身份、问答、证据快照、审批、作业恢复、消息投递
          ├── Pi SDK：理解、选算子、编排、必要时编写候选
          └── DJ 服务：检索、校验、算子验证、Run、验收、业务报告
```

不要增加每层都拥有一份 Run 状态的实现。DJ 仍是执行事实来源；应用层只持有会话、审批、任务引用和交付记录。现有 PlanWorkflow 提取成不依赖 DSH 的模块，DSH 和 Pi 各自提供 adapter。UI 的 Cordis/slot 接线需要改写，业务数据结构与渲染逻辑可复用，不能承诺原插件直接插入 Pi。

### 1. 少量深工具，而非让模型学习整个后端

优先改善现有工具契约，工具数量不是目标：

- inspect_input 返回有界样本、字段映射、数据量及未知项。
- search_capabilities 支持行为、模态、local/API 执行分支、资源约束；返回候选适用性与明确不足，按需扩展候选。
- schema 提供输入输出字段、缺失值策略、示例、资源分支。可把 top 候选的简短契约随搜索返回，减少机械往返，完整 schema 仍按需读取。
- prepare_plan 在后端做类型检查、字段衔接和运行准备评估；错误返回合法示例与具体恢复动作。
- get_run 返回结构化交付摘要及逐项验收，不让模型从多个大日志猜业务结论。

不要在工具内部悄悄再套一个完整规划 agent。后端隐藏的是确定性复杂度。

### 2. 规则表达先于自定义算法

提供基于已有统计或标签的 all/any/not、区间、集合成员、缺失值策略和分组能力。优先采用受类型检查的表达结构，不执行任意 eval。输出统一带稳定 sample_id、指标/标签、判定及原因；报告和文件交付消费同一判定。

例如人脸检测只做一次，count=0 或 count≥2 是后续规则。猫狗/实拍任务需要标签判定与分组，不能硬塞进仅接受数值 Filter 的 image_audit。完整审计全量评分与早停过滤的成本不同，应在方案中表达。

### 3. 自定义开发成为有边界的工作项

缺口确认后固定输入输出、已有证据、少量代表样本和可验证验收；只开发这个缺口。开始可使用同一 agent 的隔离上下文，不必建立多 agent 团队。

生成候选 → 静态/契约预检 → 真正执行时计费计预算 → 返回 expected/actual 和有限输出预览 → 有界修复 → 取得不可变 candidate_id → 回到原方案。

保留业务验收，修正断言路径；不能靠删除断言换取通过。修正候选以版本关联，不用改名规避预算。依赖、样例文件和权限隔离沿用 DJ 机制。对于不可信代码，需 OS/容器隔离；更换 SDK 不提供这种隔离。

### 4. 后台完成必须成为产品事件

审批后立即返回已派发回执并释放模型。后台监控 Run，终态时以 run_id + report_version 建唯一交付键，持久写入 outbox。消费者幂等写入会话结果卡，离线重连仍能看见。再按需让模型依据结构化证据润色；模型不可用时模板报告也能完成交付。

这是至少一次投递加幂等消费，不承诺网络意义的恰好一次。需处理用户取消、结果删除、账号归属、事件重放及新版本报告。底层作业成功、文件交付齐全和语义验收分别展示。

### 5. 只对实质歧义追问

从样本能查到的先查；用户已给的继续有效；低影响默认可明确说明。猫狗同框怎样归类、允许发送图片到远程 API 等会影响结果/资源边界时集中询问。保持当前准确 Plan 审批，不增加固定需求确认。未来自动运行策略应成为明确保存的用户授权，不能由 agent 自行推断。

### 6. 无进展治理与模型选择

记录当前目标、候选、已加载契约、未决问题、candidate_id 和 pending_action。恢复只补未完成动作。常规规划与复杂开发分开设置输出/时间预算，超限保存证据、返回具体失败，不用一句“立即调用工具”的 prompt 代替机制。

预算以回归调优，不能把全部任务硬锁为一次检索。无新证据时才触发恢复策略；供应商支持的 reasoning 配置、文本/图像能力和工具流式协议要实测。先用相同模型比较 harness，再用相同 harness 比较模型，避免把模型变化归功于框架。

## 实施顺序与验收

1. **共享后端修复**：规则组合、嵌套断言、预算计数点、结构化失败证据、结果摘要及终态消息。DSH 也立即获益。
2. **Pi 纵向样例**：独立入口接同一个 DJ，跑通明确文本清洗和真实缺口开发；保留正式审批和刷新恢复。不要先搬全部 UI。
3. **同条件对照**：复用 12 个规划案例，但其原协议禁止自定义且不到正式运行，应保持独立；另建完整执行集，不修改旧 gold 来迎合新产品。
4. **通过后迁移 UI**：先聊天、方案确认、结果与下载，再算子库和多账号。旧会话只读保留，新入口通过业务 task/plan/run ID 续接；不直接转换未知会话格式。双入口审批共用同一事实来源与幂等键。

执行集至少覆盖：无歧义文本；一次业务追问；人脸 OR 规则；猫狗实拍/API 分支；真实自定义 Mapper；嵌套断言失败恢复；预算拒绝；缓存缺失；模型或工具断线；批准后刷新；Run 终态主动汇报；取消与重放；跨账号访问。

衡量首个有用动作、可审批方案耗时、剔除用户等待后的总耗时、有效/无效工具调用、输出 token、正式执行成功率、硬验收通过率和终态交付延迟。低成本确定性用例每种配置重复至少三次，记录失败样本；有费用的模型集另有预算。建议目标：明确任务无额外需求确认、简单 OR 无自定义、重复提交无重复 Run、断线可恢复、终态 5 秒内结果卡可见。这些是目标，不是本次实测成果。

**选择门槛：Pi 若未提高完成率/可维护性，或迁移 UI 成本明显高于修复 DSH，就保留改进后的 DSH。当前证据足以推荐优先验证路径，不足以声称任一框架性能已胜出。**
